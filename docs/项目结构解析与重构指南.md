## 二、架构现状分析

### 2.1 当前架构模式

当前采用 **简化的分层架构**，但存在层次边界模糊的问题：

```
┌─────────────────────────────────────┐
│  UI 层 (pages + view)               │  ← IndexPage 直接调用 PlayerService
├─────────────────────────────────────┤
│  业务逻辑层 (service)               │  ← PlayerService 包揽了过多职责
├─────────────────────────────────────┤
│  数据模型层 (bean)                  │  ← 模型简单，缺少验证/转换
├─────────────────────────────────────┤
│  数据访问层                         │  ← ❌ 缺失！直接硬编码测试数据
└─────────────────────────────────────┘
```

### 2.2 核心模块依赖关系

```
EntryAbility.ts
    └── 加载 HomePage.ets

HomePage.ets ──路由跳转──> IndexPage.ets

IndexPage.ets
    ├── 引用 MiniPlayer.ets (底部播放栏)
    ├── 引用 PlayerService (初始化播放器)
    └── 引用 TestData (获取测试歌曲)

PlayerPage.ets
    ├── 引用 PlayerService (播放控制)
    ├── 引用 LyricView.ets
    └── 引用 PlayListView.ets

MiniPlayer.ets
    └── 引用 PlayerService (状态监听)

PlayerService.ets (单例)
    ├── 引用 SongInfo, PlayerState, LyricInfo
    ├── 引用 LyricParser
    └── 依赖 @ohos.multimedia.media (AVPlayer)
```

## 三、重构机会识别

### 3.1 🔴 高优先级问题

| 问题 | 位置 | 影响 | 重构建议 |
|------|------|------|----------|
| **PlayerService 职责过重** | `service/PlayerService.ets` (649行) | 单一类管理播放、状态、列表、歌词，难以维护和测试 | 拆分为 `PlayerController` + `PlayListManager` + `LyricManager` |
| **缺少数据访问层** | 全局 | 页面直接依赖测试数据，无法对接真实 API | 新增 `repository/` 和 `datasource/` 层，实现接口抽象 |
| **状态管理混乱** | `pages/`, `view/` | 各页面独立监听 PlayerService，状态同步易出错 | 引入全局状态管理（如 AppStorage 或自定义 Store） |
| **IndexPage 过大** | `pages/IndexPage.ets` (510行) | 包含4个Tab内容，代码臃肿 | 将每个 Tab 拆分为独立组件 |

### 3.2 🟡 中优先级问题

| 问题 | 位置 | 重构建议 |
|------|------|----------|
| **回调式监听易出错** | `PlayerService` 中的 `setOnXxxChange` | 改用 ArkUI 的 `@Watch` 或事件总线 |
| **硬编码图片/文字** | `IndexPage.ets` | 提取为配置或从 ViewModel 获取 |
| **缺少错误边界处理** | 各页面 | 添加错误提示、重试机制 |
| **日志输出过多** | `PlayerService.ets` | 使用分级日志，生产环境减少输出 |

### 3.3 🟢 低优先级优化

| 问题 | 重构建议 |
|------|----------|
| 常量分散 | 统一常量管理，按模块拆分 |
| 样式硬编码 | 提取为资源或样式常量 |
| 缺少单元测试 | 为 Service 层添加测试 |

## 五、关键文件详细分析

### 5.1 PlayerService.ets —— 最需重构的文件

**当前问题：**
- 649 行代码，职责过多
- 同时管理：AVPlayer 实例、播放状态、播放列表、歌词加载
- 使用回调函数进行状态通知（易内存泄漏）
- 错误处理分散在各方法中

**重构方向：**
```typescript
// 拆分后：PlayerController 只负责播放控制
class PlayerController {
  private avPlayer: AVPlayer;
  play(song: SongInfo): Promise<void>;
  pause(): Promise<void>;
  seek(time: number): Promise<void>;
  // 只暴露播放相关能力
}

// PlayListManager 管理队列逻辑
class PlayListManager {
  private songs: SongInfo[];
  next(): SongInfo;
  previous(): SongInfo;
  setMode(mode: PlayMode): void;
}

// LyricManager 管理歌词
class LyricManager {
  load(url: string): Promise<LyricInfo>;
  getCurrentLine(time: number): LyricLine;
}
```

### 5.2 IndexPage.ets —— 最臃肿的文件

**当前问题：**
- 510 行，包含4个 Tab 的完整实现
- 硬编码大量图片 URL 和文字
- 直接初始化 PlayerService（应在全局或 Ability 中初始化）

**重构方向：**
```typescript
// 精简后的 IndexPage 只保留框架
@Entry
@Component
struct IndexPage {
  build() {
    Column() {
      Tabs() {
        TabContent() { MyTab() }      // 提取为独立组件
        TabContent() { CloudVillageTab() }
        TabContent() { RecommendTab() }
        TabContent() { DiscoveryTab() }
      }
      MiniPlayer()
    }
  }
}
```

## 七、重构风险与注意事项

1. **AVPlayer 状态机复杂**：拆分 PlayerService 时需确保 AVPlayer 生命周期管理正确
2. **状态同步**：重构状态管理时，注意 MiniPlayer 和 PlayerPage 的状态一致性
3. **路由跳转**：当前使用 `@ohos.router`，后续如需支持后台播放，考虑迁移到 Navigation
4. **兼容性**：鸿蒙 API 版本差异，确保重构后仍能在目标设备运行
